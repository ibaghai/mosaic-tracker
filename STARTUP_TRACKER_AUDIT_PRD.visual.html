Startup Tracker — Audit + PRD

Hybrid design / product doc focused on the dream-job finder and networking workflow. Generated 2026-04-27.

1. Executive summary

The app is a strong market-intelligence tool — it scrapes startups, indexes jobs, and scores resume fit well. It is a weak job-hunting tool — once you've found a great job and drafted outreach, the app forgets you ever did, and the gap between "I see this opportunity" and "I'm in a conversation about it" is filled with manual copy-paste.

Biggest single hole outreach_drafts has created_at but no sent_at / replied_at / status (db/models.py:197). The entire networking feature is fire-and-forget; the app cannot tell you who you've messaged, who replied, or what's overdue. Everything else in this doc is downstream of that.

What's working well

  • Deterministic + LLM scoring pipeline (shortlist_jobs + Groq)
  • Resume PII handling — only de-identified profile + hash stored
  • Apollo caching layer with 30-day freshness
  • Strong analyst surfaces: Pulse, Trends, Coverage, Roles, Skills

What's weak

  • No application/outreach lifecycle tracking
  • No mailto: / Gmail integration — copy-only outreach
  • No saved/applied/dismissed state per job
  • Two parallel front doors (/fit, /jd-match) with forked components
  • Three orphan pages not in the sidebar (/radar, /analyst, /compare)

PRD — Top 5

Each item has a problem statement, user story, proposed change, acceptance criteria, success metric, and effort estimate.

1. Outreach lifecycle: sent / replied / status + "My Outreach" page

P0Effort: MUnblocks: 2, 3
Problem
outreach_drafts stores generated drafts but has no lifecycle columns (db/models.py:197). Once you copy a message, the app loses track of it forever — no sent state, no reply tracking, no follow-up surface.
User story
As a job hunter, I want to see who I've messaged, who replied, and what's overdue for a follow-up — so my pipeline doesn't live in my head.
Proposed change
Schema: add sent_at, replied_at, reply_text, status (draft|sent|replied|no_reply|bounced), parent_attempt_id, follow_up_due_at to outreach_drafts (or split into outreach_attempts).
UI: new /outreach page listing all drafts grouped by status, with filters (archetype, company, status, overdue).
Acceptance criteria
  • Marking a draft "sent" stamps sent_at and schedules a follow-up due-date.
  • "My Outreach" page renders < 500ms with 200 drafts.
  • An "Overdue follow-ups" badge appears in the sidebar when ≥ 1 item is overdue.
  • Reply logging accepts free-text + a quick category (positive / neutral / negative / interview).
  • Drafts persist across sessions (no per-session loss).
Success metric
≥ 70% of generated drafts have a non-draft status within 7 days of creation (i.e. the user is actually moving them forward in the app).

2. One-click mailto: / Gmail compose from DraftCard

P0Effort: SDepends on: 1, 4
Problem
Today the user copies the message body, then the email, then the subject — three separate clipboard operations — then opens a mail client and pastes them in (fit/page.tsx:539). Highest-friction step in the entire flow.
User story
As a job hunter, I want one button that opens my email client with the recipient, subject, and body all filled in — and marks the draft as "sent" when I click it.
Proposed change
In the shared DraftCard (see #4), replace "Copy message" with two primary buttons:
[Open in mail] — generates mailto:<email>?subject=...&body=... and on click POSTs to /outreach/{id}/sent.
[Open in Gmail] — generates https://mail.google.com/mail/?view=cm&to=...&su=...&body=....
"Copy" stays as a tertiary action.
Acceptance criteria
  • Clicking either button opens the user's mail client with all 3 fields populated correctly (encoded for special chars).
  • Click also fires the "mark sent" mutation; UI shows the sent state without a full page reload.
  • Body is editable in-place before clicking send (so users can add a personal line).
  • If the person has no email, the buttons are replaced with "Open LinkedIn" linking to linkedin_url.
Success metric
Median time from "drafts appear" to "marked sent" drops below 60s (vs the current never-recorded baseline).

3. Per-job state (saved / applied / dismissed) + "My Pipeline"

P0Effort: MUnblocks: 5
Problem
job_postings has scraper-driven status only (db/models.py:50). After scoring 40 jobs, the user has no way to mark which they've saved, applied to, or want to ignore. Each session re-scores the same jobs from scratch.
User story
As a job hunter, I want to mark a job "saved" or "applied" and see all my in-flight jobs in one place — so I'm not scrolling through 500 listings every session.
Proposed change
Schema: new table user_job_status (job_id, status, action_at, outcome, outcome_at, notes). Status enum: saved | applied | interviewing | rejected | offered | dismissed.
UI: star + status pill on every FitCard, /jobs row, and /companies/[id] job row. New /pipeline page grouped by status.
Acceptance criteria
  • Star button is one click and updates without reload.
  • Dismissed jobs are hidden from /fit and /jd-match results by default (with a "show dismissed" toggle).
  • /pipeline page renders with kanban-style columns by status.
  • Status changes log to a per-job timeline (visible on /companies/[id]).
Success metric
≥ 30% of fit-scored jobs receive a status update within their first appearance (proxy for "the user found this useful").

4. Hoist DraftCard / TailoredResumeBlock / ReachOutPanel into shared components

P1Effort: SPre-req for: 2, 5
Problem
These three components are copy-pasted between fit/page.tsx and jd-match/page.tsx with subtle behavioural divergence (resume upload-in-panel works on /jd-match but not /fit). A comment in the code already flags this.
User story
As a developer / future you, I want one source of truth for the outreach UI so a fix in one place fixes both pages.
Proposed change
Create dashboard/src/components/outreach/ with:
DraftCard.tsx, TailoredResumeBlock.tsx, ReachOutPanel.tsx.
Reconcile the local-file vs page-file behaviour to the page-file version (simpler) and document via TS prop types.
Acceptance criteria
  • Both /fit and /jd-match import from the new location; no inline copies remain.
  • Behaviour is identical on both pages (verified with a manual smoke test on each).
  • TypeScript build passes; no new ESLint warnings.
Success metric
Diff impact: a single-line change to DraftCard now affects both pages (verified by editing one prop and observing both pages).

5. "Score this against my resume" link from /companies/[id] and /jobs rows

P1Effort: SDepends on: 3 (session resume)
Problem
To score a job, the user has to memorise its ID and walk over to /fit manually. The link from /jobs exists (jobs/page.tsx:295) but the company-detail page has no such affordance.
User story
As a job hunter browsing a company I love, I want to click "Score" on any of their jobs and immediately see how I match — without leaving the page or re-uploading my resume.
Proposed change
Add a [Score] button to every job row on /companies/[id] (and harmonise the existing one on /jobs).
If a session resume is loaded, render the result inline in a side-panel; otherwise prompt for upload.
Result panel re-uses FitCard from /fit (extract to shared component as part of #4).
Acceptance criteria
  • Score button visible on every active job row in /companies/[id].
  • With a loaded resume, the score appears in < 4s without navigation.
  • Without a resume, an inline upload prompt appears and the score follows automatically.
  • The score result is cached so re-clicking is instant.
Success metric
≥ 50% of fit-scoring sessions originate from a "Score" button on a company or jobs page (vs the current "navigate to /fit" flow).

7. Rollout

PhaseItemsWhy this order
Week 1 #4 Shared components Cheapest item, no schema change. Stops the divergence and clears the way for #2 and #5 to land in both pages from a single edit.
Weeks 2–3 #1 Outreach lifecycle, #2 One-click send #1 is the schema move; #2 lights up the user-visible win on top of it. Together they convert outreach from fire-and-forget into a tracked workflow.
Week 4+ #3 Job pipeline state, #5 Score from job row #3 needs another schema change but unlocks the "/pipeline" surface and makes #5 instant. With #5 the discovery → score → reach out → track loop closes.
End state after all 5 The user's mental model collapses from "scoring tool + manual job hunt spreadsheet" into a single tracked pipeline. Every job they care about has a status; every outreach has a lifecycle; every action takes one click.

8. Out of scope (explicitly)

These came up in the audit but are deliberately deferred — they're either large investments or premature for current usage:

Deferred — bigger investments

  • User accounts / multi-tenant — currently single-operator. Defer until there's a second user.
  • Resume version library (multiple resumes saved per user) — wait until #3 proves session-resume is enough.
  • Editable parsed-resume + parsed-JD — valuable but requires LLM round-trip + diff UI. Re-evaluate after #1.
  • Batch outreach (send to 5 dream jobs at once) — depends on #1 + #2 being battle-tested.

Deferred — nice-to-have polish

  • Sidebar entries for /radar, /analyst, /compare (1-line fix, batch with any future Sidebar work).
  • URL-persisted filters on /jobs and /companies.
  • /jobs pagination beyond 500 rows.
  • Outreach template library / saved voices.
  • CRM-style person notes + tags.
  • must-have vs nice-to-have skill weighting in fit scoring.
